## 1. 한 줄 목표

네이버 블로그 URL 또는 본문을 넣으면, **블로그 원본 이미지를 본문 흐름에 맞춰 우선 배치**한 30~60초 9:16 숏폼 영상 초안을 만들고, 사용자가 장면별 문구·이미지를 고친 뒤 미리보기·MP4 다운로드까지 하게 한다.

## 2. 핵심 사용자와 흐름

- 사용자(한 명): 자기 블로그 글을 숏폼으로도 올리고 싶은 블로그 운영자 🟡
- 흐름: URL/본문 입력 → (자동) 구조 추출·분석·대본·장면 구성 → 대본 확인 → 장면 편집 → (자동) TTS·자막·합성 → 미리보기·MP4 다운로드

## 4. 범위

| 구분 | 내용 |
|---|---|
| 필수 | URL/본문 입력, 블로그 구조 추출(문단·이미지 순서), 30~60초 Hook·본문·CTA 대본, 장면 4~6개, 원본 이미지 우선 매칭(부족 시 반복), 장면별 문구·이미지 수정(블로그 이미지 선택·업로드), 장면별 TTS, 번인 자막, 이미지 모션(줌·팬), 9:16 MP4 합성, 미리보기·다운로드 |
| 도전(필수 완료 후) | 음성 종류 선택, 배경음악, 작업 내역 저장, 장면 전환 효과(페이드 외) |
| 보류 | 장면별 AI 이미지 생성·재생성 |
| ⛔ 제외 | 네이버 외 블로그 파싱, 스톡 이미지·영상 API, 효과음, AI 영상 생성, 로그인·회원, 결제, SNS 업로드, 별도 자막 파일, Remotion. 그 밖에 관리자 페이지, 권한 관리, 커뮤니티, 통계 대시보드, 고급 영상 편집 |

로그인·회원·소셜 로그인·결제·관리자·권한·커뮤니티·통계·고급 편집은 기업 요구사항 명세에서 "금지"가 아니라 **후순위(P2, FR-LP-01~08)**다. ✅ 결정(10/29): 일정상 이번 과제에서는 ⛔로 두고 AI가 제안하지 않는다.

참고 서비스(슈퍼쇼츠, 2026-10-29 공개 페이지·사용가이드·FAQ 기준)에서 **가져온 것**: 랜딩형 URL 입력 + 휴대폰 프레임 예시, 편집 화면 3단 구성(장면 목록 | 휴대폰 미리보기 | 이미지 패널), 렌더 결과와 같은 모양의 미리보기, 장면 단위 음성 재생성 안내, 결과 화면 FHD 표시·전송 화질 안내. 상세 명세는 `frontend/CLAUDE.md` 5·6장.
**가져오지 않은 것**(⛔, MVP 밖): 로그인·크레딧, 대본 유형 3종 선택, 영상 디자인 템플릿, 자막 스타일·위치 편집, 소제목·부가정보 오버레이, 인트로보드, 이미지 슬롯(한 장면 여러 컷), 내 목소리 녹음, 영상 길이 선택, 스톡 검색, 자동 효과음. 음성 선택·BGM은 원래대로 도전 과제.

Figma 2-B의 스톡 미디어·효과음, 2-C의 "자막 애니메이션"은 과제 필수 범위에 없어 제외했다. 스톡은 API 키·라이선스 확인이 추가로 들고, 기업은 "비는 공간은 기존 이미지로"라고 답했다.

## 5. 파이프라인 (2안 기반 확정본)

```
[네이버 블로그 URL 또는 본문]
  ① 블로그 구조 추출      (코드) 제목·소제목·문단·이미지를 원본 순서대로 blocks[]로. 이미지는 서버로 내려받아 저장
  ② 텍스트·이미지 관계    (코드) 각 이미지에 앞뒤 문단 ID를 연결. 캡션 있으면 포함
  ③ 분석 + 대본 + 장면    (LLM 1회, JSON 출력) 핵심 요약·핵심 포인트(analysis), Hook·본문·CTA 대본, 장면 4~6개, 장면별 근거 blockIds·추천 imageId·모션
  ④ 미디어 매칭 보정      (코드) LLM이 고른 imageId 검증 → 빈 장면은 원본 이미지 순서대로 반복 → 0장이면 needsUpload
  ── 사용자: 대본 확인 · 장면 편집 ──
  ⑤ 장면별 TTS           (API) 문구가 안 바뀐 장면은 캐시 재사용
  ⑥ 음성 타이밍·자막      (코드) 장면 길이 = 음성 길이, 장면 안 자막은 글자 수 비율로 분할
  ⑦ 영상 렌더링          (FFmpeg) 이미지 9:16 맞춤 + 줌/팬 + 자막 번인 + 음성 연결
  → MP4 출력
```

2안과 달라진 점:
- Figma 2안의 ⑤ "부족한 미디어 보완(스톡·AI 이미지·타이포)"은 기업 답변에 따라 **원본 반복 + 업로드**로 대체
- ⑥ "미디어 분석"은 MVP에서 생략(이미지 크기만 읽음)
- 3안의 "원본 정보 ID 유지"는 장면의 `sourceBlockIds` 필드로만 흡수(근거 추적·사실 왜곡 점검용)
- ③에서 분석·대본·장면을 LLM 한 번으로 묶음. 이유: 호출 비용·지연 감소, 한 번의 JSON 검증으로 끝남. 품질이 부족하면 분석/대본 2회로 쪼갠다 🟡

## 6. API·데이터 계약 (프론트·백엔드 공통 원본)

### 6-1. 데이터 모양

```ts
type ProjectStatus =
  | "extracting"     // ① 구조 추출 중
  | "scripting"      // ②~④ 분석·대본·장면 구성 중
  | "ready"          // 사용자 편집 가능
  | "rendering"      // ⑤~⑦ TTS·자막·합성 중
  | "done"           // MP4 완료
  | "error";

type Stage = "extract" | "script" | "tts" | "subtitle" | "render";

interface Project {
  id: string;
  status: ProjectStatus;
  progress: { stage: Stage; percent: number; message: string } | null;
  error: { stage: Stage; code: ErrorCode; message: string } | null;
  source: {
    type: "url" | "text";
    url: string | null;
    title: string | null;
    blocks: Block[];
  };
  assets: Asset[];                 // 이 프로젝트에서 쓸 수 있는 이미지 전체(블로그 + 업로드)
  needsUpload: boolean;            // 블로그 이미지 0장
  analysis: {                      // ③ 결과. 기업 요구 FR-AI-01(핵심 내용 요약). ✅ 추가(10/29)
    summary: string;               // 원문 핵심 요약 2~3문장
    keyPoints: string[];           // 핵심 포인트 3~5개, 각 한 문장
  } | null;                        // ③ 전에는 null
  script: { hook: string; body: string; cta: string; estimatedSec: number } | null;
  scenes: Scene[];                 // 4~6개
  video: { url: string; durationSec: number; width: 1080; height: 1920; fps: 30 } | null;
  createdAt: string;               // ISO 8601
}

interface Block {
  id: string;                      // "b1", "b2" ...
  type: "heading" | "paragraph" | "image";
  text: string | null;             // heading·paragraph 본문, image는 캡션
  assetId: string | null;          // image일 때만
  linkedBlockIds: string[];        // image일 때 앞뒤 문단 ID (②의 결과)
}

interface Asset {
  id: string;                      // "a1" ...
  origin: "blog" | "upload";
  url: string;                     // 백엔드가 서빙하는 주소 (/api/assets/{id})
  width: number;
  height: number;
}

type Motion = "zoom_in" | "zoom_out" | "pan_left" | "pan_right" | "none";

interface Scene {
  id: string;                      // "s1" ...
  order: number;                   // 1부터
  role: "hook" | "body" | "cta";
  text: string;                    // 내레이션 = 자막 원문
  assetId: string | null;          // null이면 업로드 필요
  motion: Motion;
  sourceBlockIds: string[];        // 근거 문단
  durationSec: number | null;      // TTS 후 확정, 그 전엔 null
  subtitles: { startSec: number; endSec: number; text: string }[]; // 장면 기준 상대 시간
}

type ErrorCode =
  | "NOT_NAVER_URL" | "POST_NOT_FOUND" | "EXTRACT_FAILED"
  | "TEXT_TOO_SHORT" | "LLM_FAILED" | "TTS_FAILED"
  | "RENDER_FAILED" | "MISSING_IMAGE" | "UPLOAD_INVALID"
  // ✅ 추가(10/29, 백엔드 B2에서 사람 승인): 공통 오류 형식에 쓸 범용 코드
  | "NOT_FOUND"        // 404: 없는 프로젝트·이미지·경로. 프론트는 "작업 만료" 안내
  | "INVALID_REQUEST"  // 422(405 포함): 요청 형식 오류
  | "INVALID_STATE";   // 409: 지금 상태에서 할 수 없는 요청(예: rendering 중 PATCH)
```

- `assetId`는 프로젝트를 넘어 전역에서 유일하다(`GET /api/assets/{assetId}`에 프로젝트 ID가 없으므로). 위 `"a1"`은 예시일 뿐, 실제 값은 백엔드가 정한 임의 문자열이다. 프론트는 형식을 가정하지 않는다.

### 6-2. 엔드포인트

| 메서드·경로 | 요청 | 응답 | 설명 |
|---|---|---|---|
| `POST /api/projects` | `{ type: "url", url }` 또는 `{ type: "text", text }` | `202 { id }` | 작업 생성, ①~④ 백그라운드 시작 |
| `GET /api/projects/{id}` | — | `200 Project` | 상태 조회. 진행 중엔 프론트가 1.5초 간격 폴링 |
| `PATCH /api/projects/{id}/scenes` | `{ scenes: [{ id, text?, assetId?, motion? }] }` | `200 Project` | 장면 수정. `status`가 `ready`·`done`·`error`일 때만 허용. 수정 시 `video`는 null로, `status`가 `done`이면 `ready`로. **`text`가 바뀐 장면은 `durationSec=null`, `subtitles=[]`로 되돌린다**(프론트는 이것으로 "음성 다시 만듦" 장면을 표시). `assetId`·`motion`만 바뀐 장면은 그대로 둔다 |
| `POST /api/projects/{id}/regenerate` | — | `202 { id }` | 대본·장면 다시 생성(③④만) |
| `POST /api/projects/{id}/assets` | multipart `file` (jpg/png/webp, 10MB 이하) | `201 Asset` | 이미지 업로드 |
| `GET /api/assets/{assetId}` | — | 이미지 | 블로그·업로드 이미지 서빙 |
| `POST /api/projects/{id}/render` | 선택 `{ motionQuality?: "fast" \| "smooth" }` | `202 { id }` | ⑤~⑦ 시작. 모든 장면에 `assetId`가 있어야 함. ✅ 추가(10/31, 사용자 지시): `fast` = 기존 zoompan(빠름, 약간 떨림), `smooth` = 보간(부드러움, 합성이 더 오래 걸림). 생략하면 `smooth` |
| `POST /api/projects/{id}/render?from=subtitle` | 위와 같은 선택 본문 | `202` | 실패한 단계부터 재시도(완료된 TTS 재사용). `motionQuality`를 바꿔도 음성은 다시 만들지 않고 영상 합성만 새로 한다 |
| `GET /api/projects/{id}/video` | — | `video/mp4` | 미리보기·다운로드(`?download=1`이면 attachment) |
| `GET /api/health` | — | `{ ok: true }` | 백엔드 실행 여부 확인 |

오류 응답 공통 형식: `{ "error": { "code": ErrorCode, "message": "사용자에게 그대로 보여줄 한국어 문장" } }`

## 11. 바이브코딩 공통 규칙

1. **한 번에 한 기능만 요청한다.** "장면 편집 화면 전부"가 아니라 "장면 카드 목록 + 문구 수정"처럼 쪼갠다.
2. **AI에게 이 문서와 해당 MD를 먼저 읽힌 뒤 시작한다.** 계약(6장)과 다른 필드명을 만들면 거절한다.
3. **매 요청 끝에 직접 실행해서 확인한다.** 화면은 브라우저로, API는 `/docs`(FastAPI 자동 문서)로.
4. **키·비밀값은 코드와 저장소에 넣지 않는다.** `.env`는 `.gitignore`, 배포 환경변수로만.
5. **AI가 범위 밖 기능(⛔ 표기)을 추가하면 지운다.**
6. **작업이 끝나면 커밋한다.** 커밋 메시지에 무엇을 확인했는지 한 줄.
7. 막히면 같은 요청을 세 번 넘게 반복하지 말고, 오류 전문과 기대 동작을 정리해 새 대화에서 다시 시작한다.
